# Advanced Encryption Patterns

The earlier patterns illustrate field selection. These advanced sketches add key-version and transformation metadata; they still require an external key system, access model, and execution tests.

For a more detailed guide on these topics, please see the **[Advanced Encryption Patterns in the Encrypting Data tutorial](/data-security/encrypt-data/step-4-advanced-patterns)**.

## Pattern 1: Multi-Key Strategy

Using a single encryption key for all data is risky. A better pattern is to use separate keys for different data types based on their risk level. This is known as **risk-based encryption**.

- **`CARD_ENCRYPTION_KEY_HEX`**: For PCI-DSS data. Highest security, most frequent rotation.
- **`PII_ENCRYPTION_KEY_HEX`**: For GDPR/CCPA/HIPAA data (SSN, email). High security.
- **`ADDRESS_ENCRYPTION_KEY_HEX`**: For location data.
- **`TEMPORAL_ENCRYPTION_KEY_HEX`**: For sensitive dates.

This strategy limits the "blast radius" if a single key is ever compromised. You implement this by simply calling the `encrypt_aes` function with the appropriate key environment variable for each field, as demonstrated in the previous steps.

## Pattern 2: Transformation audit metadata

The following processor emits authored metadata about which transformation ran and why. A real audit design needs an independently protected destination, access rules, retention, and tested failure handling.

```yaml title="Add an Audit Log Processor"
- mapping: |
    root = this

    # Create an audit log entry
    let audit_log = {
      "event_id": uuid_v4(),
      "action": "ENCRYPT_PII",
      "timestamp": now(),
      "fields_encrypted": [
        "payment.card_number", "customer.ssn", "customer.email" // etc.
      ],
      "compliance_standards": ["PCI-DSS", "GDPR", "HIPAA"],
      "pipeline_id": "encrypt-production-v3"
    }

    # Send metadata to a separately managed audit endpoint
    _ = http_client(
      env("AUDIT_ENDPOINT_URL"),
      {"verb": "POST", "timeout": "2s"},
      audit_log
    )
```

## Pattern 3: Key Versioning & Decryption

To handle key rotation, store the key version and nonce alongside the ciphertext.
The rotated key below remains deployment-managed, must contain 64 hexadecimal
characters, and fails closed unless it decodes to exactly 32 bytes.

```yaml title="Validated rotated card key"
- mapping: |
    root = this
    let key = env("CARD_ENCRYPTION_KEY_V2").decode("hex")
    let key = if $key.length() != 32 {
      throw("Expected CARD_ENCRYPTION_KEY_V2 to decode to 32 bytes")
    } else { $key }
    let previous_key = env("CARD_ENCRYPTION_KEY_V1").decode("hex")
    let previous_key = if $previous_key.length() != 32 {
      throw("Expected CARD_ENCRYPTION_KEY_V1 to decode to 32 bytes")
    } else { $previous_key }
    let nonce = uuid_v4().hash("sha256").slice(0, 12)
    root.payment.card_number_nonce = $nonce.encode("base64")
    root.payment.card_number_encrypted = this.payment.card_number.string().encrypt_aes("gcm", $key, $nonce).encode("base64")
    root.encryption_metadata.card_key_version = env("KEY_VERSION").or(throw("KEY_VERSION is required"))
    root.payment = root.payment.without("card_number", "cvv")
```

A corresponding decryption service would parse the version and select the
validated active or previous key. Historical decryption still depends on
retained keys, authorization, metadata integrity, and tested recovery
procedures.
