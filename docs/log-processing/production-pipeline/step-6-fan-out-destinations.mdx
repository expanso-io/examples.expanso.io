# Fan-Out Destinations

This architecture configures Elasticsearch, S3, and a local file as parallel destinations. Each destination remains an external dependency with its own delivery and retention contract.

## Goal

- **Elasticsearch:** Configured searchable destination
- **S3:** Configured object-storage destination
- **Local File:** Configured on-site destination

## Configuration

We use the `broker` output pattern with `fan_out`.

### 1. The Broker Output

```yaml
output:
  broker:
    pattern: fan_out
    outputs:
      - stdout:
          codec: lines
      - http_client:
          url: ${ELASTICSEARCH_HTTPS_URL}/logs-${!timestamp_unix_date()}/_doc/${! uuid_v4() }
          verb: PUT
          headers:
            Authorization: ApiKey ${ELASTICSEARCH_API_KEY}
            Content-Type: application/json
          tls:
            enabled: true
            root_cas_file: ${ELASTICSEARCH_CA_FILE}
      - aws_s3:
          bucket: ${S3_BUCKET}
          path: logs/${!timestamp_unix_date()}/${!uuid_v4()}.jsonl.gz
          batching:
            count: 1000
            period: 30s
            processors:
              - compress:
                  algorithm: gzip
          server_side_encryption: aws:kms
          kms_key_id: ${S3_KMS_KEY_ARN}
```

### 2. Handling Failures

In a fan-out, if one output fails, we don't want to block the others. The `fan_out` pattern handles this, but individual outputs can also have their own fallback (e.g., write to disk if S3 is down).

## Troubleshooting

| Issue                    | Solution                                           |
| ------------------------ | -------------------------------------------------- |
| One output blocks others | Use `drop_on_error: true` on unreliable outputs    |
| S3 connection fails      | Check credentials and bucket permissions           |
| File output missing      | Verify the output directory exists and is writable |
